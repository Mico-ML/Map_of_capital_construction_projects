## 1. Роль, контекст и правила работы

Ты — **senior fullstack-инженер и архитектор геоинформационных систем** с опытом разработки государственных веб-порталов (React + TypeScript + Node.js + PostgreSQL/PostGIS + 2GIS Maps API). Дополнительно ты — продуктовый аналитик, умеющий превращать ведомственные реестры в понятные гражданам инструменты.

**Заказчик:** Министерство строительства Тульской области.
**Продукт:** публичный интерактивный портал о результатах деятельности Министерства и строительной отрасли региона.
**Цель:** повысить информированность граждан о строящихся и введённых объектах капитального строительства (ОКС) и дать инструмент оценки реальной доступности социальной инфраструктуры.

**Аудитория (три сегмента — учитывай каждый в UI):**
1. **Граждане** — без специальной подготовки, мобильные устройства, нужны простые ответы: «что строят рядом со мной», «когда откроют», «как подать жалобу».
2. **Сотрудники органов власти и СМИ** — аналитика, выгрузки, срезы по МО/отраслям/подрядчикам, контроль сроков.
3. **Подрядчики и заказчики** (служебная зона, этап 2) — актуализация данных, фотофиксация, ответ на жалобы.

**Правила работы (соблюдай строго):**
- Работай **итерациями по плану из §12**. После каждой итерации выдай работающий код + краткий отчёт «что сделано / что дальше / какие решения приняты». Не пытайся выдать всё одним ответом.
- **Перед стартом итерации 0** задай мне до 5 уточняющих вопросов, если чего-то критично не хватает. Дальше вопросы не задавай — принимай решения сам и фиксируй их в `docs/DECISIONS.md`.
- **Не выдумывай данные.** Если значения нет в CSV — поле `null` + признак «нет данных» в UI. Все синтетические данные помечай `isMock: true` и визуальным бейджем «ДЕМО-ДАННЫЕ» в интерфейсе.
- **Не выдумывай API.** Используй только те эндпоинты 2ГИС, что перечислены в §5. Если нужной возможности нет — предложи реализуемый обходной путь и объясни его в README.
- **Ключи и секреты** — только `.env` (файл `.env.example` с пустыми значениями в репозитории). Никаких ключей в коде, README и логах.
- **Все запросы к внешним API (кроме инициализации MapGL в браузере) идут через бэкенд-прокси** с кэшированием и rate limiting. Это требование безопасности и экономии квот.
- Интерфейс, комментарии к коду, commit-сообщения и документация — **на русском языке**. Идентификаторы в коде — на английском.
- Пиши код production-качества: TypeScript в strict-режиме, типизированные контракты API (общие типы frontend/backend), обработка ошибок, отсутствие `any`.

## 2. Что нужно получить на выходе (объём MVP)

Монорепозиторий, поднимаемый одной командой `docker compose up`, содержащий:

| Артефакт | Требование |
|---|---|
| Frontend (SPA) | Публичная часть портала: карта, карточка объекта, слои «До/В процессе/После», изохроны, «светофор» соцнагрузки, карта удовлетворённости, форма жалобы, аналитический дашборд |
| Backend (REST API) | Служит данные, проксирует 2ГИС, считает производные метрики, хранит жалобы и медиа, OpenAPI-спецификация в `/api/docs` |
| ETL-скрипт | Нормализация `objects.csv` → PostgreSQL/PostGIS (правила в §6), идемпотентный, с отчётом о качестве данных |
| Seed-данные | 95 объектов из CSV + мок-данные по закупкам, обращениям, соцобеспеченности, камерам, снимкам «до/после» (Приложение C) |
| Админка (минимум) | Модерация жалоб, ручная корректировка координат и атрибутов, загрузка фото/рендеров — на MVP достаточно простых CRUD-экранов под ролью `admin` |
| Документация | `README.md` (запуск, переменные окружения, скриншоты), `docs/ARCHITECTURE.md`, `docs/DATA_MODEL.md`, `docs/API.md`, `docs/DECISIONS.md`, `docs/ROADMAP.md` |
| Тесты | Unit-тесты ETL и расчёта метрик, e2e (Playwright) на 5 ключевых сценариев §13 |
| Docker | `docker-compose.yml` (app, api, db, tile/media-сервер по необходимости), миграции и сиды выполняются автоматически |

**Режим работы по умолчанию — `MOCK`**: приложение полностью функционально без внешних ключей, кроме ключа MapGL для отрисовки карты (без него показывай понятную заглушку с инструкцией, где взять демо-ключ).

## 4. Обязательные требования к 2ГИС: факты, которые нужно использовать

> Ниже — проверенные сведения. Используй именно их, не придумывай другие эндпоинты.

**4.1 MapGL JS API (отрисовка карты)**
- Подключение: npm-пакет `@2gis/mapgl` (loader со скриптом `https://mapgl.2gis.com/api/js/v1`) либо напрямую тег `<script>`.
- Инициализация: `await mapgl.load(); const map = new mapgl.Map('container', { key: MAPGL_KEY, center: [37.6173, 54.1947], zoom: 8.4, style: ... })`.
- Центр по умолчанию — Тула `[37.6173, 54.1947]`, стартовый вид — вся Тульская область (подбери zoom так, чтобы область входила целиком, и ограничь панорамирование `minZoom`/`maxBounds` по региону).
- Ключ получает пользователь на `https://platform.2gis.ru` (демо-ключ). Ключ MapGL — публичный, но домен-ограничения задаются в кабинете; вынеси в `VITE_MAPGL_KEY`.
- Слои своих данных: GeoJSON-источники + слои стиля (полигон, линия, точка, подпись) либо `mapgl.Marker` / кластеризация. Для >200 точек кластеризация обязательна.
- **Растровые подложки:** `mapgl.RasterTileSource` поддерживает **WMS и WMTS** (URL-функция от `x, y, zoom, bbox`, bbox в EPSG:3857). Обязательно указывай `attribution` (копирайт источника снимков). Именно этим способом подключаются архивные спутниковые снимки (§7, Ф3).
- Для геопривязки одиночных изображений (архитектурный рендер) используй реализуемый в MapGL способ (растровый источник с одним изображением через свой тайл-сервис, либо DOM-оверлей с пересчётом координат через проекцию карты). Выбранный способ зафиксируй в `docs/DECISIONS.md`.

**4.2 Isochrone API (зоны пешей доступности)**
```
POST https://routing.api.2gis.com/isochrone/2.0.0?key=ROUTING_KEY
Content-Type: application/json
{ "start": { "lat": 54.1947, "lon": 37.6173 }, "durations": [600, 900], "reverse": false, "transport": "walking" }
```
- Ответ: `{ "isochrones": [{ "duration": 600, "geometry": "MULTIPOLYGON(((...)))", "start_point": {...}, "attract_points": [...] }], "format": "wkt", "transport": "walking", "status": "OK" }`.
- Ограничения: до **5 промежутков времени**, каждый **≤ 3600 секунд**. `reverse: true` — «от границ к точке» (нужно для задачи «кто дойдёт до объекта»).
- **WKT → GeoJSON** конвертируй на бэкенде (`wellknown`/`wkt-parser`), результат сохраняй в PostGIS-таблицу `isochrone_cache` (см. §6.3). Повторный запрос к API при кэш-попадании запрещён.
- Ключ Isochrone/Routing API — **секретный**, только на бэкенде.

**4.3 Geocoder API (геокодинг адресов)**
```
GET https://catalog.api.2gis.com/3.0/items/geocode?q=<адрес>&key=<KEY>&fields=items.point,items.address
```
- Используй для доопределения координат объектов без них (§6.4) и для поиска адреса пользователем.
- Результаты геокодинга сохраняй с признаком источника (`manual` / `geocoder` / `csv`) и уровнем уверенности; неоднозначные случаи отправляй на ручную модерацию в админке.

**4.4 Search API (POI внутри изохроны)**
- Для подсчёта социальных объектов (детсады, школы, поликлиники, спортсооружения, ДК) внутри построенной изохроны используй Search API 2ГИС (`catalog.api.2gis.com/3.0/items`) с фильтрацией по рубрикам и полигону. **Перед использованием сверь актуальные имена параметров и рубрикаторов с документацией** (`https://docs.2gis.com/api/search/`) и вынеси список рубрик в конфиг `config/poi_rubrics.ts`. Не хардкодь ID рубрик в логике.

**4.5 Общие правила работы с 2ГИС**
- Все вызовы 4.2–4.4 — через бэкенд-прокси: единая точка `/api/v1/geo/*`, кэш (TTL изохрон — 30 суток, геокод — 90 суток), rate limit на IP и на пользователя, ретраи с экспоненциальной задержкой (макс. 3), обработка `status != "OK"` и квот, метрики по расходу квот.
- 2ГИС предоставляет **MCP-сервер для AI-агентов** (`https://docs.2gis.com/api/ai/mcp-server/overview`) — упомяни в README как способ быстрой проверки геоданных при разработке.
- **Важно: у 2ГИС нет архива спутниковых снимков прошлых лет.** Слой «До» реализуется из открытых архивов (Sentinel-2 с 2015 г., 10 м; Landsat с 1984 г., 30 м) через собственный тайл/WMS-сервер (GeoServer/MapServer/TileServer) либо из фотоархива заказчика. Слои 2ГИС при этом остаются базовой подложкой и источником POI/зданий.

**4.6 Проверено фактически на рабочем ключе (12.09.2026) — используй как данность**

| Что проверено | Результат |
|---|---|
| **Тульская область в 2ГИС** | `region_id = 36` — зашить в конфиг `config/regions.ts`, передавать во все запросы Geocoder/Search |
| Isochrone API | **Работает.** `POST /isochrone/2.0.0` для Тулы (54.1947, 37.6173; `durations:[600,900]`; `walking`) вернул `status:"OK"`, `format:"wkt"`, два `MULTIPOLYGON`, `generation_time:0` |
| Geocoder API | **Работает**, `page_size` до 10, поддерживает `fields=items.adm_div` (обязательно запрашивай — без него валидация невозможна) |
| Search API + геометрия | **Работает с `point`+`radius` И с параметром `polygon`.** Формат `polygon` — **WKT**: `POLYGON((lon lat,lon lat,…))` и `MULTIPOLYGON(((lon lat,…)))`. Формат «lon,lat;lon,lat» **отклоняется** с `Invalid geometry field format`. Следствие: геометрию из ответа Isochrone API можно передавать в Search API **напрямую, без конвертации** — это основной пайплайн Ф4 |
| Routing API (`/route/2.0.0/json`) | Вернул **HTTP 418** — на текущей подписке/параметрах недоступен. В MVP не требуется; если понадобится «маршрут до объекта», согласуй с 2ГИС отдельно и не закладывай это в архитектуру |
| `/3.0/regions` | Вернул `Unknown API method` — справочник регионов из API не получать, `region_id` хранить в конфиге |
| Рубрикатор POI | Ответ содержит `items.rubrics[{id, alias, name, parent_id}]` и `items.purpose_name` (например, «Школа») — сопоставление сфер Ф4/Ф5 строить по `rubrics.alias` из конфига, а не по тексту названия |

> **Ограничение демо-ключа:** расход квот не виден в ответах, поэтому кэш и прокси (§4.5) — обязательны. Ключ хранить только в `.env` / `.env.local` (в репозитории — `.env.example` без значений, `.gitignore` содержит `.env*`). В кабинете 2ГИС ограничить ключ списком доменов.

| Экспертиза | 49 записей, формат «от ДД.ММ.ГГГГ № 71-1-1-3-038991-2019», бывает несколько экспертиз в одной ячейке, встречаются опечатки (`№ №`) | Хранить как массив структур `{date, number, raw}` |
| НП/ГП, ФП, Код проекта | НП/ГП заполнено у 66, ФП у 40, код проекта у 16; названия госпрограмм в 4+ вариантах написания | Справочники программ с алиасами, нормализация |
| Даты контракта/ЗОС/акта | во многих строках **одинаковые значения** (признак заполнения «пакетом») | Не интерпретировать как ошибку, но вывести в отчёте качества |

**ETL должен печатать отчёт о качестве данных** (`reports/data_quality.md` + JSON): сколько записей, сколько пропусков по каждому полю, сколько значений нормализовано, какие объекты не удалось геокодировать, какие дубли найдены. Это обязательный артефакт.

## 6. Модель данных и ETL

### 6.1 Правила нормализации (обязательные)

1. Парсинг CSV: разделитель `;`, пропуск 3 строк заголовка, склейка парных колонок (`lat`/`lon`, `zos_date`/`zos_no`, `act_date`/`act_no`).
2. Пустые значения: `''`, `-`, `—`, `0` и `0,00` в текстовых и смысловых полях → `null` (исключение: числовая готовность, где `0` — валидное значение; различай по колонке).
3. Числа: убрать неразрывные и обычные пробелы-разделители тысяч, запятая → точка, `parseFloat`.
4. Даты: `ДД.ММ.ГГГГ` → `DATE` (ISO). Диапазоны (`15.09.2022-28.10.2022`, `29.12.2021 – 31.03.2023`, в т. ч. с en-dash и пробелами) → `{start, end, raw}`. Год из полной даты — `EXTRACT(YEAR)`.
5. Кавычки в названиях организаций — унифицировать в «ёлочки» `«»`, регистр сохранять, дубли сливать через таблицу алиасов.
6. МО: маппинг всех вариантов написания к эталонному справочнику `municipalities` (20 МО из CSV + полный справочник МО Тульской области с кодами ОКТМО — подгрузить эталон из конфигурации, не из CSV).
7. Отрасль: нормализация к справочнику (§Приложение B); при `null` — восстановление по ГРБС (например, «Министерство энергетики ТО» → «Энергетика», «Министерство сельского хозяйства, природных ресурсов и экологии ТО» → «Сельское хозяйство и экология», «АМО г. Тула» → требует ручной модерации, помечать `industry_source = 'inferred'`).
8. Статус: сохранить исходное значение + вычислить `status_group` (`design` / `construction` / `procurement` / `completed`).
9. Каждую исходную строку сохранять **целиком** в `objects.raw JSONB` + `source_row_number` + `imported_at` + `source_file_hash` — чтобы любую производную цифру можно было сверить с первоисточником и чтобы реестр расширялся без переделки схемы (номера колонок в источнике идут с пропусками).
10. ETL **идемпотентный**: повторный импорт того же файла обновляет записи по `(source_row_number, source_file_hash)` и не создаёт дубли; ручной ввод в админке не затирается (флаг `manual_override` по полям).

### 6.3 Геокодинг и геометрии МО

> Ниже — не теория: алгоритм и цифры получены прогоном всех 95 записей через Geocoder API 2ГИС. Эталонные скрипты лежат рядом с этим промптом — `scripts/geocode_check.py` (прямой геокодинг со скорингом) и `scripts/reverse_check.py` (верификация обратным геокодированием), отчёты — `data/geocode_report.md`, `data/geocode_suggestions.csv`, `data/reverse_geocode_check.csv`. Перенеси их в репозиторий (`etl/geocode/`) и развивай, а не пиши геокодинг с нуля.

**Измеренные результаты — обязательно учитывай в продукте:**

| Проверка | Результат |
|---|---|
| Объектов с координатой в CSV | 58 из 95 |
| Обратное геокодирование этих 58 точек | **45 подтверждены** (район/населённый пункт совпал), 6 — частично, 6 спорных (5 из них — ложные срабатывания эвристики на «Тула городской округ», «Узловский», «Славный»), **1 реальная ошибка данных** |
| Найденная реальная ошибка | Объект №7 «Крытый тренировочный манеж … в г. Туле (Косая гора)» имеет координату `54.488002, 37.700203` → обратный геокод: **Ясногорск, Ясногорский район**, тогда как Косая Гора — `54.0986, 37.5731` (Тула городской округ). Расхождение ~43 км. Автоматический контроль качества обязан ловить такие случаи |
| 37 объектов без координат | уверенно геокодируются только **10** (2 high + 8 medium), 16 — слабое совпадение, 6 — геокодер вернул другой населённый пункт (отклонено валидатором), 5 — не найдено |
| Объектов вообще без адреса | **21** — геокодинг невозможен в принципе |
| Наивный геокодинг «адрес → первый результат» | **непригоден**: 25 из 53 записей дают расхождение >500 м, 16 — более 10 км. 2ГИС подменяет одноимённые улицы: «г. Алексин, ул. Героев Алексинцев» → «Тула, Большая улица, 8»; «р.п. Чернь, ул. К. Маркса» → «ул. Карла Маркса, Тула»; «п. Куркино» → бизнес-центр в Туле |

**Правила геокодинга (обязательные):**

1. **Координата из CSV всегда приоритетнее результата геокодера.** Геокодер применяется только чтобы (а) заполнить пустые координаты и (б) верифицировать имеющиеся. Автоматическая перезапись CSV-координаты запрещена.
2. Запрашивай `fields=items.adm_div` и **валидируй кандидата по цепочке административного деления**: ожидаемое МО — из колонки «АМО», при её отсутствии (`0` в 24 записях) — из текста адреса. Кандидат принимается только при совпадении района/городского округа. Несовпадение → `rejected` с фиксацией причины.
3. Скоринг кандидата: район (+3) → населённый пункт (+3) → улица (+2) → номер дома (+1); несовпадение района (−3). `high` — score ≥ 6 и преимущество перед вторым кандидатом; `medium` — ≥ 5; `low` — ≥ 1; иначе `rejected`.
4. Верификация существующих координат — **обратным геокодированием** (`q=lat,lon`): сравнение `adm_div` точки с ожидаемым МО. Расхождение → в отчёт качества и очередь модерации (так найден объект №7).
5. Для 21 объекта без адреса — извлекать населённый пункт из **наименования** ОКС («Школа … в микрорайоне Суворовский 2, г. Тула»), помечая `geocode_source='inferred_from_name'` с пониженным доверием.
6. Результат писать в БД с полями `geocode_source` (`csv`/`geocoder`/`manual`/`inferred_from_name`), `geocode_confidence` (`high`/`medium`/`low`), `geocode_candidates` (JSON), `geocode_verified_at`. В админке — экран «Уточнить точку»: карта, список кандидатов со скорингом, ручной ввод координат, обязательное подтверждение оператором (`manual`).
7. **Организационный вывод (зафиксировать в README и в отчёте):** геометрию активных объектов нельзя получить автоматически — требуется официальный запрос координат по 42 активным объектам, в первую очередь по 21 объекту без адреса. До этого в UI честно показывать счётчик «объектов без точного местоположения: N», размещать такие объекты на центроиде МО с пометкой «местоположение уточняется» и **не включать** их в расчёт изохрон и «светофора» без явного согласия пользователя на приближённую геометрию.

**Границы МО и население:**
- Границы МО загрузить GeoJSON-скриптом `scripts/load_municipalities.ts` (эталон — ОКТМО/данные OSM). При отсутствии эталона — упрощённые полигоны с флагом `is_mock`, чтобы заказчик подменил их официальными. Принадлежность объекта к МО определять через `ST_Contains` в PostGIS, а не по тексту адреса.
- Население и плотность — адаптер `PopulationProvider` (Росстат/перепись, данные операторов связи); на MVP `data/mock/population.csv` с указанием источника и года.

## 7. Функциональные требования

### Ф1. Карта и работа с объектами
- Базовая карта 2ГИС с центром на Тульской области, ограничением области видимости регионом, переключателем «схема / спутник (если доступно) / гибрид», масштабом, компасом, геолокацией пользователя (с явного согласия).
- Маркеры объектов: иконка по **отрасли**, цвет/обводка по **статусу** (`status_group`), размер по мощности/площади (опциональный режим). Кластеризация при zoom < 12 и при совпадении координат (2 известные пары дублей — обязательно разводить).
- Панель фильтров (слева, сворачиваемая): отрасль (мультивыбор), статус, группа статуса, МО (мультивыбор + поиск), собственность, ГРБС, заказчик, подрядчик, год ввода/год окончания (диапазон + таймлайн-слайдер), строительная готовность (слайдер), наличие фото/камеры, «только объекты рядом со мной», текстовый поиск по названию/адресу/подрядчику.
- Счётчики: «показано N из 95», сводка по фильтрам (сколько введено, сколько строится, суммарная площадь, средняя готовность).
- Список объектов рядом с картой (виртуализация), синхронизация «список ↔ карта» (hover, клик, выделение), сортировка (по году ввода, готовности, названию, удалённости), режим таблицы с экспортом.
- Режим «сравнение объектов» (до 3): таблица ключевых атрибутов + мини-карты.
- Deep linking: URL объекта `/objects/:id`, состояние фильтров в query-параметрах (ссылку можно отправить/распечатать).

### Ф2. Карточка объекта (публичная)
Вкладки/блоки:
1. **Сводка**: наименование, отрасль, статус, группа статуса, готовность (прогресс-бар с процентом), собственность, МО, адрес (нормализованный + «как в источнике»), год начала/окончания, год ввода, площадь, мощность (значение + единица + исходная строка), код проекта, НП/ГП и ФП.
2. **Участники**: ГРБС, заказчик, подрядчик (кликабельно → фильтр по организации), контакты.
3. **Сроки и документы**: передача ЗУ, разрешение на строительство, контракт (дата и период), сроки строительства, экспертиза(ы) — список с датами и номерами, ЗОС (дата/номер), акт ввода (дата/номер), дата установки техоборудования, дата гидравлических испытаний.
4. **Закупки**: блок из Ф6.
5. **Фото/видео и «До–В процессе–После»**: блок из Ф3.
6. **Доступность**: блок из Ф4 (кнопка «показать зону пешей доступности», расчёт на месте).
7. **Обращения и жалобы**: связанные жалобы (публичные, обезличенные) + кнопка «сообщить о проблеме» (Ф8).
8. **История места**: что было на участке до начала работ (барак под расселение / промзона / сквер / пустырь / иное), текстовое описание, период, источник данных.
9. **Паспорт объекта**: печать/скачивание PDF одной страницы (брендированный шаблон: герб/логотип, наименование, атрибуты, QR-код на страницу объекта) + кнопка «Поделиться».
10. **Таймлайн**: хронология ключевых событий (ЗУ → РНС → контракт → начало СМР → ЗОС → акт ввода → год ввода), вертикальная шкала с датами; для активных объектов — плановые даты из контракта и отметка «сегодня», подсветка просрочки.
11. **Прозрачность**: «показать исходную запись реестра» (raw JSONB) — для проверяющих и журналистов.

Требования: все пустые значения отображаются как «Нет данных» (не пустыми ячейками и не прочерками вперемешку); даты — `ДД.ММ.ГГГГ`; числа — с пробелом-разделителем тысяч; у каждого производного показателя — тултип «как считается».

### Ф3. Слои «До / В процессе / После» + таймлапс
- Переключатель трёх состояний: **До** (архивный снимок/фото места + блок «история места»), **В процессе** (фотохронология со стройплощадки + живые камеры), **После** (архитектурный рендер с геопривязкой).
- **Режимы сравнения**: шторка (swipe-слайдер), бок о бок, плавное наложение с регулятором прозрачности, «было/стало» одной кнопкой. Все режимы — с одинаковым центром/zoom/углом камеры (синхронизация вьюпорта).
- **Таймлапс**: слайдер по датам (по месяцам/годам) + кнопка «воспроизвести» (автоматическая смена кадров с настраиваемой скоростью), лента миниатюр внизу. Кадры — из `media_assets` (kind = `before_sat` / `process_photo` / `camera_snapshot`).
- **Архивные снимки «До»**: поскольку архива снимков у 2ГИС нет — подключаешь Sentinel-2 (с 2015 г.) / Landsat (с 1984 г.) через собственный WMS/WMTS-источник (`mapgl.RasterTileSource`), предобработанные мозаики без облачности по годам; обязательный копирайт источника в `attribution`. На MVP: интерфейс + адаптер `HistoricalImageryProvider` с мок-тайлами/мок-изображениями и документированной процедурой подготовки реальных мозаик (скрипт + инструкция в `docs/IMAGERY.md`).
- **Камеры подрядчика**: адаптер `CameraProvider`; поддержка HLS (через `hls.js`), снимков по расписанию (refresh_sec) и статичных кадров; на MVP — заглушки (статичное изображение + псевдо-«живой» таймстемп), интерфейс реального подключения (URL потока, токен, интервал, привязка к объекту, чекбокс «согласие подрядчика получено»). Обязательна метка времени последнего кадра и состояния «камера недоступна».
- **«После»**: загрузка рендера в админке с геопривязкой (4 угла или bounds), предпросмотр, версия/дата, автор, лицензия. Если рендера нет — блок «Материалы не предоставлены» + форма запроса у заказчика.

### Ф4. Пешая изохрона 10–15 минут (ключевой инструмент оценки доступности)
- По клику на объект — кнопка «Зона пешей доступности»: запрос Isochrone API (`transport: "walking"`, `durations: [600, 900]`, настраиваемо 5/10/15/20 мин), отрисовка полупрозрачных полигонов с градацией по времени + легенда.
- Переключатель направления: **«от объекта»** (куда можно дойти) и **«к объекту»** (`reverse: true` — откуда жители дойдут до него). Для садов/школ/поликлиник основной сценарий — «к объекту».
- Внутри изохроны — подсчёт и отображение релевантных POI: передавай WKT-геометрию изохроны в Search API **напрямую** параметром `polygon` (проверено: `MULTIPOLYGON` принимается без конвертации, формат «lon,lat;lon,lat» — нет), плюс `region_id=36`; для образования — детсады и школы; для здравоохранения — поликлиники/амбулатории/стационары; для спорта — спортсооружения и площадки; для культуры — ДК, библиотеки, музеи; плюс жилые дома/население (оценка охвата). Сопоставление сфер — по `items.rubrics[].alias` и `items.purpose_name` из конфига `config/poi_rubrics.ts`, не по тексту названий.
- **Отчёт доступности** в карточке: население/число домов в зоне, список конкурентных объектов той же сферы в зоне (с расстоянием и временем пути), вердикт («закрывает дефицит в МО Х» / «дублирует существующий объект») — с пояснением методики в тултипе.
- Пакетный режим (для аналитиков): построить изохроны для всех объектов отрасли/МО, показать сводную карту покрытия территории и «белые пятна» — зоны области, не покрытые пешей доступностью объектов сферы.
- Обязательны: кэширование в PostGIS, индикатор загрузки, обработка ошибок/квот, дисклеймер «расчёт по пешеходной сети 2ГИС, является оценкой».

### Ф5. «Светофор» социальной нагрузки муниципалитетов
- Хороплетная карта МО Тульской области с классификацией по обеспеченности в 5 сферах: **образование, здравоохранение, спорт, энергетика, культура**.
- Переключатели: сфера (5 + «сводный индекс»), год, режим отображения: `обеспеченность`, `плотность населения`, `дефицит с учётом плотности` (композит).
- **Методика расчёта (реализуй явно и вынеси в конфиг):**
  - `provision_index = actual_capacity / (normative_per_1000 × population / 1000)`;
  - `actual_capacity` = сумма мощностей действующих объектов сферы в МО + мощности строящихся ОКС (из реестра, с весом по году ввода и готовности — строящиеся объекты учитываются как «перспективная мощность», переключаемо «с учётом строящихся / только действующие»);
  - `normative_per_1000` — из справочника `normatives` (нормативы градостроительного проектирования, например СП 42.13330.2016: дошкольные — 61 место на 1000 жителей, школы — 113 мест на 1000 жителей и т. п.). **Значения — конфигурируемые, с пометкой «требуют утверждения заказчиком»**;
  - классы: `deficit` — индекс < 0,7 (**красный**, повышенная нагрузка/дефицит); `border` — 0,7–1,0 (**жёлтый**); `normal` — 1,0–1,5 (**светло-зелёный**); `surplus` — > 1,5 (**тёмно-зелёный**, повышенная обеспеченность). Пороги — в конфиге;
  - композитный индекс — средневзвешенное по сферам (веса в конфиге) с поправкой на плотность населения: `pressure = (1 - provision_index) × normalized_density` — чем плотнее население при том же дефиците, тем выше приоритет.
- Клик по МО → панель drill-down: таблица по 5 сферам (факт/норматив/индекс/класс), численность и плотность населения (источник и год), список объектов сферы в МО (действующие + строящиеся), динамика за годы, кнопка «показать объекты МО на карте».
- Обязательные элементы честности данных: у каждого значения — источник и дата; при отсутствии данных по сфере — нейтральная штриховка «нет данных» (не зелёный и не красный); легенда с пояснением «что означает цвет»; дисклеймер о методике и о том, что данные по плотности населения могут происходить из разных источников (Росстат / операторы связи).

### Ф6. Карточка по активным объектам: данные о закупках
- В карточке объекта блок «Закупки и контракт»: реестровый номер закупки/контракта, предмет, способ определения поставщика, дата заключения, НМЦК/цена контракта, этап исполнения, статус, сроки исполнения, сведения об исполнителе, информация об изменениях/расторжении, аванс, гарантии, источник (ЕИС / региональный портал малых закупок / ручной ввод), ссылка на первоисточник, дата последнего обновления.
- Дополнительно: «стоимость за м² / за место» (производный показатель с пометкой методики), индикатор риска (срок истёк, а готовность < 100 %; неоднократные переносы).
- **Реализация по гибридному принципу (§10):** в MVP — адаптер `ProcurementProvider` с мок-данными (правдоподобные, помеченные как демо, привязанные к реальным подрядчикам/срокам из CSV) и полностью готовым интерфейсом; боевое подключение — отдельным этапом через официальные механизмы (открытые данные/выгрузки ЕИС `zakupki.gov.ru`, сервисы закупок малого объёма `zakupki.tularegion.ru`, либо регламентный обмен по соглашению). **Скрапинг ЕИС в MVP не реализовывать** — вместо этого подготовь `docs/INTEGRATION_EIS.md` с юридически корректными вариантами получения данных и схемой обмена.

### Ф7. Тепловая карта удовлетворённости граждан
- Источник — агрегированные данные по ответам на обращения граждан (ПОС «Госуслуги. Решаем вместе», электронная приёмная Правительства ТО, отраслевые обращения).
- Метрика по МО × отрасль × период: `satisfaction_index = f(доля положительных/решённых ответов, медианное время ответа, доля просроченных, доля повторных обращений, число обращений на 1000 жителей)`. Формулу реализуй в одном месте (`services/satisfaction.ts`), покрой unit-тестами, параметры и веса — в конфиге, методику — в тултипе и в `docs/METHODOLOGY.md`.
- Визуализация: два режима — (а) **хороплет по МО** с градацией цвета (зелёный → красный), (б) **тепловая карта по точкам обращений** (плотность). Если MapGL не поддерживает тип слоя `heatmap` — реализуй тепловую карту одним из способов: hexbin/агрегация по сетке + полигональный слой с градацией (предпочтительно, воспроизводимо), либо генерация растровых тайлов на бэкенде + `RasterTileSource`, либо canvas/Deck.gl-оверлей поверх карты. Выбранный способ обоснуй.
- Фильтры: отрасль, период (месяц/квартал/год), тип обращения, статус решения. Drill-down: список обращений по МО (обезличенный: категория, дата, срок ответа, результат), топ-5 проблемных тем.
- Связь с картой объектов: подсветка объектов в МО с низкой удовлетворённостью по соответствующей отрасли; переход «жалобы по этому объекту» из карточки.
- На MVP — мок-датасет обращений (Приложение C), согласованный по структуре с реальной выгрузкой, чтобы замена источника не требовала переделки UI.

### Ф8. Подача жалобы на состояние строительного объекта
- Публичная форма (без авторизации — с ограничением и капчей; с авторизацией через ЕСИА — с расширенными возможностями и статусом в личном кабинете).
- **Категории (строго как справочник, расширяемый):** строительный мусор; разбитая/повреждённая дорога; грязь на выезде со стройплощадки; нарушение графика производства шумных работ; техника без тента при перевозке сыпучих материалов; отсутствие информационного стенда (паспорта объекта); ограждение/зона безопасности; пыль и выбросы; иное (с обязательным комментарием).
- Поля: категория, объект (автоподстановка из реестра по геометрии/поиску + «объекта нет в списке»), геометка (клик по карте или координаты устройства), адрес/ориентир, описание (10–1000 символов), фото/видео (до 5 файлов, ≤10 МБ, JPG/PNG/MP4, извлечение EXIF-даты и геолокации), согласие на обработку персональных данных (обязательный чекбокс, текст по 152-ФЗ), контакты для ответа (опционально при анонимной подаче).
- Поведение: клиентская валидация, черновик в localStorage, защита от повторной отправки, оценка «похожая жалоба уже есть» (по категории и радиусу 100 м) с предложением поддержать существующую, выдача номера обращения и страницы отслеживания.
- Жизненный цикл: `new → in_review → accepted → forwarded (в ПОС/электронную приёмную/подрядчику) → resolved | rejected`; SLA по категории (в справочнике); уведомления автору (email/СМС-заглушка на MVP); публичная лента «решённые проблемы» (обезличенная, до/после).
- Модерация в админке: очередь, просмотр фото, скрытие персональных данных, назначение ответственного, комментарий, смена статуса, экспорт, аудит всех действий (`audit_log`).
- **Интеграция:** адаптер `FeedbackChannelProvider` с реализациями `mock` (MVP), `pos_gosuslugi` (Платформа обратной связи, «Госуслуги. Решаем вместе»), `gov_to_reception` (электронная приёмная Правительства Тульской области). Требования к боевому этапу — в §10 и `docs/INTEGRATION_POS.md`: формат передачи обращения, получение идентификатора (`pos_ticket_id`), синхронизация статусов, требования к авторизации через ЕСИА (OIDC), журналирование.
- Анти-спам: rate limit (не более 3 обращений с IP за 10 минут), капча, фильтр дублей, блокировка по ключевым словам — конфигурируемо.

### Ф9. Сквозная функциональность
- **Аналитический дашборд** (`/analytics`): объекты по статусам и отраслям (кольцевые/столбчатые), динамика ввода по годам (2022 — 11, 2023 — 10, 2024 — 14, 2025 — 18), суммарная площадь и мощность, средняя готовность активных объектов, топ-10 подрядчиков и заказчиков по числу объектов, распределение по МО (карта + бар-чарт), «объекты риска» (истёк срок контракта при готовности < 100 %; готовность не растёт; отсутствует фотофиксация > N месяцев), количество обращений и жалоб по категориям.
- **Поиск**: глобальная строка (объекты, адреса, организации, МО) с подсказками; поиск по карте через Geocoder 2ГИС.
- **Экспорт**: CSV/XLSX/GeoJSON текущей выборки, PDF-паспорт объекта, PDF/PNG-снимок карты с легендой, печать.
- **Главная страница портала**: заголовок и миссия, ключевые цифры (всего объектов, введено в этом году, строится сейчас, охвачено МО), «объекты недели», быстрые сценарии («Что строят рядом со мной», «Сад/школа в 15 минутах ходьбы», «Сообщить о проблеме»), блок «Отрасли», ссылки на первоисточники данных.
- **Служебная зона** (роли `editor` / `moderator` / `admin`): список объектов с редактированием, очередь геокодинга, загрузка медиа и рендеров, справочники, модерация жалоб, отчёт о качестве данных, журнал аудита.

- Пустые состояния и ошибки: понятный текст + действие («нет объектов по фильтрам — сбросить фильтры», «сервис 2ГИС недоступен — повторить / показать данные без карты»).
- Дисклеймеры: о статусе данных («данные актуальны на ДД.ММ.ГГГГ»), о методиках расчётов, о демо-данных.

## 9. Нефункциональные требования

- **Производительность:** загрузка главной ≤ 3 с (LCP) при среднем канале; отклик карты на фильтр ≤ 200 мс; расчёт изохроны с кэшем ≤ 300 мс, без кэша — с индикатором прогресса и таймаутом 15 с; рендер 95 объектов мгновенный, архитектура выдерживает 10 000 объектов (кластеризация + серверная пагинация по bbox).
- **Надёжность:** graceful degradation при недоступности 2ГИС (показывать данные списком/таблицей), ретраи, идемпотентность операций записи, миграции только вперёд с откатом, ежедневный бэкап БД и медиа.
- **Безопасность:** валидация всех входных данных на сервере; санитизация пользовательского ввода (защита от XSS); CORS-whitelist; rate limiting; JWT с коротким TTL + refresh, OIDC/ЕСИА для авторизованных сценариев; RBAC (public / editor / moderator / admin); загрузка файлов — проверка MIME и размера, хранение вне webroot, антивирусная проверка (интерфейс-заглушка); секреты только в env; HTTPS обязателен; логирование без ПДн; **152-ФЗ**: согласие на обработку ПДн при подаче жалобы, минимизация состава данных, срок хранения, уведомление об обработке, локализация хранения ПДн в РФ.
- **Аудит и трассируемость:** `audit_log` на все изменения данных и действия модерации; каждая цифра в UI имеет источник (CSV-строка, API-ответ, расчёт с методикой).
- **Мониторинг:** структурные логи (pino), healthcheck `/api/health`, метрики расхода квот 2ГИС, алерты при превышении (на MVP — лог + панель в админке).
- **Совместимость:** две последние версии Chrome, Firefox, Safari, Edge; Яндекс Браузер; мобильные Chrome/Safari. Без обязательных плагинов.
- **On-premise:** вся система разворачивается в закрытом контуре; единственная внешняя зависимость — сервисы 2ГИС (описать в README как риск и предусмотреть возможность замены картографического провайдера через слой абстракции `MapProvider`, чтобы смена вендора не переписывала бизнес-логику).

## 10. Интеграции: принцип «мок сейчас — боевое подключение позже»

Каждый внешний сервис реализуется **за интерфейсом-адаптером** и выбирается переменной окружения (`*_PROVIDER=mock|live`). Контракт адаптера описан в OpenAPI/типах; мок-реализация возвращает структурно идентичные данные с флагом `isMock`. Боевая реализация добавляется без изменения UI и бизнес-логики.

| Интеграция | Интерфейс | MVP | Боевой этап: что требуется |
|---|---|---|---|
| Карта, изохроны, геокодинг, POI | `MapProvider`, `IsochroneProvider`, `GeocoderProvider`, `PoiProvider` | **LIVE** (ключ 2ГИС) | Подписка/квоты, договор, домен-ограничения ключей |
| ЕИС `zakupki.gov.ru`, закупки малого объёма `zakupki.tularegion.ru` | `ProcurementProvider` | **MOCK** | Соглашение об обмене / открытые данные / регламентная выгрузка; описание в `docs/INTEGRATION_EIS.md`. Скрапинг не использовать |
| ПОС «Госуслуги. Решаем вместе», электронная приёмная Правительства ТО | `FeedbackChannelProvider` | **MOCK** (сохранение в свою БД + имитация номера обращения) | Регистрация в ПОС, OIDC/ЕСИА, схема обмена обращениями и статусами, `docs/INTEGRATION_POS.md` |
| Камеры видеонаблюдения подрядчиков | `CameraProvider` | **MOCK** (HLS-заглушка/статичные кадры) | Согласие подрядчика, HLS/RTSP-эндпоинты, медиа-сервер (MediaMTX/nginx-rtmp), токены, SLA доступности |
| Архивные спутниковые снимки «До» | `HistoricalImageryProvider` | **MOCK** + `docs/IMAGERY.md` | Подготовка мозаик Sentinel-2/Landsat по годам, свой WMS/WMTS (GeoServer), либо архивные аэрофотоматериалы заказчика |
| Архитектурные рендеры «После» | `MediaStorage` | Загрузка в админке | Регламент получения у заказчиков/проектировщиков, права использования |
| Население и плотность (Росстат / операторы связи) | `PopulationProvider` | **MOCK** CSV | Официальные выгрузки Росстата по МО, договор с оператором на обезличенные данные |
| Данные об обращениях (для Ф7) | `AppealsDataProvider` | **MOCK** | Выгрузки из ПОС/электронной приёмной по отраслям и МО, регламент периодичности |
| Границы МО (GeoJSON) | `BoundariesProvider` | Скрипт загрузки (OSM/конфиг), при отсутствии — упрощённые полигоны с `is_mock` | Официальные границы (ОКТМО / картографический фонд) |

Требования к гибридному переходу: для каждой интеграции в `docs/INTEGRATIONS.md` — ответственный, способ получения доступа, формат обмена, частота обновления, деградация при недоступности, оценка трудозатрат. Переключение `mock → live` не должно требовать изменения кода UI.

## Приложение C. Требования к мок-данным (MVP)

Мок-данные должны быть **правдоподобными, внутренне согласованными и явно помеченными**:
1. **Закупки**: для всех 42 активных объектов сгенерировать контракт, согласованный с CSV (подрядчик, `contract_date`, `contract_period_start/end`, готовность). Цена — детерминированная функция от площади/мощности и отрасли (например, стоимость за м² по отрасли из конфига), округление до тыс. ₽. Обязательна пометка «демо-данные, не являются сведениями из ЕИС».
2. **Обращения/удовлетворённость**: на 20 МО × 5 отраслей × 24 месяца — количество обращений, доля решённых, медианное время ответа, доля просроченных; генерация с фиксированным `seed`, чтобы цифры не «прыгали» между запусками. Индекс удовлетворённости должен давать реалистичный разброс (включая 2–3 проблемных МО).
3. **Медиа «До/В процессе/После»**: для 8–10 объектов (обязательно включить 5 активных с координатами и 3–5 заметных введённых: детский сад в Заокском, школа в «Северной Мызе», манеж на Косой горе и т. п.) — 3–6 кадров на объект с датами; «после» — плейсхолдер-рендер с рамкой «материал предоставлен заказчиком (демо)». Все файлы — в `data/mock/media/`, в БД `is_mock=true`.
4. **Камеры**: 3 объекта с «живым» HLS-адресом-заглушкой (публичный тестовый поток или статичный кадр с обновляемым таймстемпом), у остальных — статус «камера не подключена».
5. **Население МО**: 20 МО + прочие МО области; источник-заглушка «Росстат, оценка на 01.01.2025 (демо)»; плотность вычисляется из площади полигона.
