# DECISIONS — принятые архитектурные и продуктовые решения

Фиксируются согласно §1 ТЗ: после уточняющих вопросов решения принимаются
самостоятельно и документируются здесь. Дата старта: 13.09.2026.

## D1. UI-кит: MUI (Material UI v6), не shadcn/ui + Tailwind
**Решение:** MUI. **Обоснование:** госпортал с большим объёмом табличных данных,
формами и панелями — MUI даёт готовые доступные компоненты (таб-порядок, ARIA,
фокус-ловушки, контраст), встроенную русскую локаль (`ruRU`), адаптивную сетку и
темы без ручной сборки. shadcn/Tailwind быстрее для лендингов, но потребовал бы
собирать доступные компоненты вручную, что рискованно для требования §8
(доступность, работа с клавиатуры, контраст ≥ 4,5:1). Палитра «светофора» (§8)
вынесена в `@oks/shared/config/palette` и продублирована паттернами/символами,
чтобы информация не передавалась только цветом.

## D2. Бэкенд: NestJS (не Fastify-голый)
**Решение:** NestJS 11 на Express-адаптере. **Обоснование:** модульность, DI,
декораторы валидации (`class-validator`), автогенерация OpenAPI (`@nestjs/swagger`),
`@nestjs/throttler` для rate limiting — всё из коробки, что соответствует требованиям
§2 (OpenAPI в `/api/docs`), §9 (RBAC, лимиты, валидация). Fastify быстрее, но для
MVP важнее структура и экосистема; при необходимости адаптер меняется без переписывания
бизнес-логики.

## D3. ORM/миграции: Prisma + PostGIS через `Unsupported` и手写 SQL-миграцию
**Решение:** Prisma 6 как типизированный клиент для скалярных полей; геометрия
(`geom`, `center`) объявлена `Unsupported("geometry(...)")` и обслуживается
`$queryRaw` (`ST_AsGeoJSON`, `ST_MakePoint`, `ST_Intersects`, `ST_Contains`).
Миграция `0001_init` сгенерирована `prisma migrate diff` + **вручную** добавлены
`CREATE EXTENSION postgis/pgcrypto` (в начало) — Prisma их не генерирует.
**Обоснование:** Prisma не поддерживает PostGIS-типы нативно, но гибрид «типизированный
клиент для атрибутов + raw SQL для гео» — устоявшийся паттерн, сохраняющий строгую
типизацию (§2 «отсутствие any») и полную мощь PostGIS. `migrate deploy` идемпотентен.
БД заменяема на Postgres Pro без переделки SQL (§3, импортозамещение): SQL стандартный.

## D4. Модульная система: CJS для shared/etl/api, ESM для web
**Решение:** `packages/shared`, `etl`, `apps/api` собираются в CommonJS
(`module: CommonJS`), `apps/web` — ESM (Vite). **Обоснование:** NestJS/Prisma/tsx
стабильнее с CJS; Vite — ESM. `shared` импортируется и теми, и другими: web через
vite-alias на исходники, api/etl через собранный `dist`. Это избегает конфликта
`require(esm)` на Node 20.

## D5. Границы и центры МО: реальные данные OpenStreetMap, не мок-полигоны
**Решение:** вместо «упрощённых полигонов с is_mock» (§6.3 допускал это) загружены
**реальные** границы 26 МО Тульской области из OSM (Overpass API, admin_level=6,
13.09.2026, ODbL), упрощение Douglas–Peucker ~85 м. Контроль: суммарная площадь
25 610 км² против эталона области ~25 679 км² (отклонение 0,27 %), все 26 колец
замкнуты. Центроиды, площади и ОКТМО (ОК 033-2013, ред. 01.09.2026: городские округа
70 7xx, муниципальные районы 70 6xx, муниципальные округа 70 5xx) — в эталонном
справочнике `@oks/shared/dictionaries/municipalities`. **Обоснование:** реальные
границы делают «светофор» (Ф5) и определение МО через `ST_Contains` (§6.3) настоящими,
а не демонстрационными. `geom_is_mock=false`, источник и дата — в атрибутах. Замена на
официальные границы (ОКТМО/картофонд) — на этапе 2 без переделки кода (тот же GeoJSON-контракт).

## D6. Принадлежность объекта к МО: приоритет колонки «АМО», геометрия — для контроля
**Решение:** итоговый `municipality_id` берётся из колонки «АМО» (если заполнена);
при её отсутствии (`0` в 24 записях) — восстанавливается из адреса, затем из
наименования (§6.3 п.5). Точка, попадающая в другое МО по `ST_Contains`/обратному
геокодированию, **не перезаписывает** колонку, а поднимает флаг
`municipality_conflict` и отправляется на модерацию. **Обоснование:** §15.10 —
координаты из реестра не считаются ошибочными только из-за расхождения с геокодером;
в этих данных чаще ошибается геокодер. Так пойман объект №7 «Косая гора».

## D7. Единица мощности «голого» числа — «мест»
**Решение:** значения мощности без явной единицы («1100», «75») трактуются как
**места** (`capacity_unit = places`), с сохранением `capacity_raw`. **Обоснование:**
заголовок колонки источника — «Мошность (кол-во мест)». Единица вынесена в
`capacity_unit` и `capacity_raw`, так что интерпретация прозрачна и обратима.
Составные значения («400 посещений, 340 коек») разбираются в `capacity_parts[]`.
Диапазоны («2500-3000м3/сут») значением не заполняются (не выдумываем) — только raw + помета.

## D8. Демо-режим геокодирования: координаты не выдумываются
**Решение:** `MockGeocoder` возвращает пустой результат (`status: provider_mock`);
объекты без координат попадают в очередь геокодирования (`pending_key`), а не
получают случайные точки. Боевой `DvaGisGeocoder` (§4.3) включается
`GEOCODER_PROVIDER=live` + `CATALOG_API_KEY`. **Обоснование:** §15.1 и ответы
заказчика (есть только ключ MapGL) — честность данных важнее «красивой» карты.
Скоринг кандидатов и валидация по `adm_div` (§6.3) реализованы и покрыты тестами,
чтобы боевой прогон сразу работал корректно.

## D9. Алиасы организаций/программ генерируются из фактических данных
**Решение:** таблицы слияния дублей (`etl/src/config/aliases_tables.ts`)
**сгенерированы** скриптом `etl/tools/generate_aliases.py` по фактическим вариантам
написания из `objects.csv`, а не набраны вручную. Ключ — «слепок» (верхний регистр,
только буквы/цифры, ё→е). **Обоснование:** исключает опечатки в кириллических ключах
и делает нормализацию воспроизводимой; каждый алиас соответствует реальной строке реестра.

## D10. Тепловая карта и «светофор» — свои слои, не «встроенный heatmap 2ГИС»
**Решение (архитектурно, реализация Ф5/Ф7 — итерация 5):** MapGL не имеет
документированного типа слоя `heatmap`, поэтому удовлетворённость визуализируется
хороплетом по МО (полигональный слой из `/municipalities/geojson`) и/или hexbin-агрегацией
на бэкенде + полигональный слой. Слои «До» — через `mapgl.RasterTileSource` (WMS/WMTS).
**Обоснование:** §15.2 — не использовать недокументированные возможности; воспроизводимость.

## D11. Аналитика-дашборд: Recharts + ленивая загрузка маршрута
**Решение:** Recharts (не ECharts) и `React.lazy` для `/analytics`. **Обоснование:**
Recharts легче и декларативнее для стандартных распределений Ф9; ленивая загрузка
не тянет ~400 КБ графиков на главную/карту (LCP ≤ 3 с, §9). Вендоры вынесены в
отдельные чанки (react/mui/charts/query) через `manualChunks`.

## D12. Формат ошибок, пагинация, ETag — по §11
Единый конверт `{ error: { code, message, details } }` (глобальный `AllExceptionsFilter`,
включая маппинг ошибок Prisma), пагинация `{ items, total, page, limit }`, `ETag` +
`Cache-Control` на справочниках. Версионирование URI (`/api/v1`), health — `/api/health`
(VERSION_NEUTRAL).

## D13. Логирование: pino-http с redact секретов
`pino-http` как middleware; `redact` исключает `authorization`, `cookie`, `key`,
`apiKey` — ключи 2ГИС и ПДн не попадают в логи (§9, §15.5, §15.11). Healthcheck
исключён из auto-логирования.

## D14. Тесты: vitest (unit), Playwright (e2e — итерация 2+)
Unit-тесты покрывают ETL (парсинг реального CSV, нормализация всех «грязных» форматов,
скоринг геокодера, контроль геометрии), формулу удовлетворённости и утилиты shared —
**133 теста зелёные** без БД. e2e-сценарии §13 подключаются по мере готовности фич
(Playwright конфиг — итерация 2). Покрытие расчёта метрик обязательно (§3) — выполнено.

## D15. Графики дашборда: inline-SVG вместо recharts
**Решение:** отказаться от recharts в пользу лёгких собственных SVG-графиков
(столбчатая + кольцевая диаграммы) в `AnalyticsPage`. **Обоснование:** recharts тянет
~590 модулей (d3-*), что раздувало бандл и приводило к исчерпанию памяти при сборке в
ограниченном контуре; собственные SVG-графики сократили граф сборки до 1086 модулей,
уменьшили бандл и LCP (§9) и не добавляют внешних зависимостей (импортозамещение, §3).
Распределения Ф9 (столбцы/кольца/таблицы) не требуют тяжёлой чарт-библиотеки.

## D16. hls.js грузится в рантайме, а не бандлится
**Решение:** `hls.js` подключается динамически (script-тег, `window.Hls`) только для
реальных HLS-камер боевого этапа; URL — `VITE_HLS_JS_URL` (для on-premise — self-host,
по умолчанию — CDN). MVP-камеры — snapshot-заглушки, hls.js не загружают.
**Обоснование:** не тянуть тяжёлую библиотеку в публичный бандл (LCP), сохранить
интерфейс HLS (§7 Ф3) и возможность self-host в закрытом контуре.

## D17. Демо-медиа «До/В процессе/После» и камеры — генерируемые SVG-плейсхолдеры
**Решение:** `etl/tools/generate_mock_media.py` создаёт для 10 показательных объектов
(5 активных с координатами + 5 заметных введённых) SVG-кадры «до/процесс/после»
(3–6 на объект) и снимки камер + `manifest.json`; сид пишет их в `media_assets`/
`camera_sources` с `is_mock=true`. Каждый кадр содержит явную пометку «ДЕМО-ДАННЫЕ ·
не является реальным фото/снимком». Раздача — read-only `/mock-media/` (статика api +
прокси nginx). **Обоснование:** §15.1 (не выдумывать реальные снимки) и Приложение C.3
(правдоподобные, детерминированные, помеченные мок-данные). Реальные мозаики
Sentinel-2/Landsat — этап 2 (`prepare_imagery_mosaic.py`, docs/IMAGERY.md).

## D18. Демо-зоны доступности: явная геометрическая модель вместо имитации API
**Решение:** при `ISOCHRONE_PROVIDER=mock` и `ISOCHRONE_MOCK_GEOMETRY=true` зона строится
детерминированной моделью `радиус(азимут) = duration × WALKING_SPEED_MPS × (1 − a/2 + a·noise)`,
`noise` — `mulberry32(seed = id объекта + длительность + число лучей)`. Такая зона помечена
`isMock=true`, `source="model"`, `api_version="demo-model"`, отдельным дисклеймером
`ISOCHRONE_DISCLAIMER_MOCK` и бейджем «ДЕМО-ДАННЫЕ» в карточке, легенде и на странице
пакетного режима. Переменная `ISOCHRONE_MOCK_GEOMETRY=false` полностью отключает
синтетику — тогда адаптер возвращает `provider_disabled`, а UI «Нет данных».
**Обоснование:** DoD итерации 4 требует работающей механики Ф4 (зоны 10/15 мин, кэш,
отчёт, пакетный режим), а ключа Isochrone API у заказчика на MVP нет (только MapGL).
Вариант «ничего не показывать» делал бы Ф4 непроверяемым, а вариант «молча рисовать круги»
нарушал бы §15.1. Выбран промежуточный: модель **явно** названа моделью, отделена в кэше
флагом `is_mock` и не может быть выдана за результат 2ГИС (кэш-выборка фильтрует
`is_mock = <текущий режим провайдера>`). Решение согласуется с принятым в итерации 3
подходом к демо-медиа (D17) и с §10 (мок возвращает структурно идентичные данные с `isMock`).

## D19. Маршруты Ф4 — по §11, а не внутри `/geo/*`
**Решение:** `GET /objects/{id}/isochrone`, `GET /objects/{id}/accessibility-report`,
`GET /isochrone/status`, `GET /isochrone/coverage`, `POST /isochrone/batch`;
статус-заглушка `GET /geo/isochrone` (итерации 0–3) удалена, в `/geo/*` остались геокодер,
рубрикатор и сводка провайдеров. Модуль `modules/isochrone` со своим `ThrottlerModule`
(тяжёлые маршруты — 20/мин, пакетный — 3/мин).
**Обоснование:** §11 ТЗ задаёт именно эти пути; выделение модуля держит бизнес-логику
отдельно от прокси (`@oks/api/src/modules/isochrone`), rate limit настраивается точечно.

## D20. Собственный WKT-парсер и отказ от маршрутов «до двери»
**Решение 1:** конвертация WKT ⇄ GeoJSON — собственный модуль `integrations/2gis/wkt.ts`
(11 unit-тестов на образцах из документации 2ГИС), а не пакеты `wellknown`/`wkt-parser`.
**Обоснование:** нужны ровно `MULTIPOLYGON`/`POLYGON` с отверстиями, нормализация в
MultiPolygon (тип колонки БД), обратная конвертация для демо-зон и отказ без подмены
геометрии; внешние пакеты тянут зависимости и работают с устаревшими форматами GeoJSON.
**Решение 2:** расстояния до соседних объектов — гаверсинус **по прямой**, время —
`distance / WALKING_SPEED_MPS`; маршруты не строятся.
**Обоснование:** Routing API 2ГИС на текущей подписке возвращает HTTP 418 (§4.6), а
выдумывать «время в пути» запрещено (§15.1). Ограничение явно показано в UI и в методике.

## D21. Площадь `polygon` в Search API > 6 км² → документированный fallback
**Решение:** если площадь зоны больше `SEARCH_POLYGON_MAX_KM2` (6 км² — лимит из
справочника `/3.0/items`), запрос выполняется `point` + `radius` (≤ 50 000 м при наличии
`q`/`rubric_id`) с постфильтрацией результатов попаданием точки в полигон; способ
возвращается в `method` и попадает в методику отчёта.
**Обоснование:** §15.2 — не использовать недокументированные приёмы; лимит площади
документирован, поэтому обходной путь тоже документирован и воспроизводим. Зона
20 минут пешком (~5 км²) находится у границы лимита — fallback обязателен.

## D22. POI в демо-режиме не выдумываются; «конкуренты» берутся из реестра ОКС
**Решение:** `MockPoiProvider` возвращает `status="provider_mock"` и пустой список —
в отчёте `count=null`, `gapReason="provider_mock"`, в UI «Нет данных» с указанием причины.
Сопоставление «объекты той же сферы» выполняется по **реальным** записям реестра ОКС
(`ST_DWithin` вокруг зоны, `origin="registry"`, `isMock=false`). Население в зоне —
произведение плотности МО (демо-население, помечено) на площадь зоны.
**Обоснование:** §15.1 (не выдумывать значения) + §8 (у каждого числа источник и дата).
Реестр даёт проверяемые факты без ключа 2ГИС, а отсутствие POI видно как пропуск данных,
а не как «ноль объектов». Дополнительно зафиксировано ограничение методики: реестр ОКС —
не полная сеть социальной инфраструктуры, поэтому вердикт предварительный и уточняется
POI 2ГИС (боевой режим) и `provision_index` (Ф5, итерация 5).

## D23. Алиасы рубрик не выдумываются — верификация через Categories API
**Решение:** в `config/poi_rubrics.ts` `rubricIds=null`, `aliases=[]`,
`verifiedAgainstDocs=false`; добавлены `queries` (для документированного `q`),
`rubricQueries` (строки для поиска рубрик), `itemType` (`building` для жилья) и
прокси `GET /api/v1/geo/rubrics?q=` к Categories API `2.0/catalog/rubric/search`.
Заполнение конфига реальными `id`/`alias` региона 36 — операция с `CATALOG_API_KEY`
(инструкция в `docs/INTEGRATIONS.md`, пункт `docs/ROADMAP.md`).
**Обоснование:** рубрикатор зависит от региона и версии каталога; публиковать
придуманные алиасы означало бы нарушить §15.2/§15.3. Механизм верификации поставляется
вместе с кодом, а не «когда-нибудь потом».

## Открытые решения (на следующие итерации)
- Хранилище медиа: локальное `/var/data/media` и read-only `data/mock/media` (MVP) →
  S3-совместимое (этап 3) за интерфейсом `StorageProvider`.
- Кэш: in-memory `cache-manager` (MVP) → Redis (этап 3); интерфейс уже допускает замену.
  Кэш изохрон и POI-снимков — в PostGIS (`isochrone_cache`), он от Redis не зависит.
- Изохроны: `transport` — только `walking` (Ф4); автомобиль/вело/ОТ API поддерживает,
  включается расширением `ISOCHRONE_TRANSPORTS` при появлении задачи (этап 3).
- `detailing` (детализация полигона) и `start_time` (статистические пробки) Isochrone API
  вынесены в конфиг/параметры, но в UI не открыты — этап 3.
- Авторизация: SHA-256 для первичного админа (MVP) → bcrypt/argon2 + JWT + ЕСИА/OIDC
  (итерация 6 / этап 2). Зафиксировано в ROADMAP.
