# METHODOLOGY — методики расчёта производных показателей

Все параметры (пороги, веса, нормативы) вынесены в конфигурацию `packages/shared/config`
и **требуют утверждения заказчиком**. Каждая цифра в UI снабжается тултипом «как считается»
и ссылкой на источник/дату. Значения без данных отображаются нейтрально («нет данных»),
а не как норма или дефицит.

## 1. «Светофор» социальной нагрузки МО (Ф5)

**Индекс обеспеченности** по сфере:

```
provision_index = actual_capacity / (normative_per_1000 × population / 1000)
```

- `actual_capacity` — сумма мощностей действующих объектов сферы в МО **плюс** мощности
  строящихся ОКС (из реестра) как «перспективная мощность» с весом по году ввода и
  готовности. Переключатель «с учётом строящихся / только действующие»
  (`social_provision.include_planned`). Минимальная готовность для учёта —
  `PLANNED_CAPACITY_WEIGHTS.minReadinessPct`.
- `normative_per_1000` — из справочника `normatives` (примеры СП 42.13330.2016: дошкольные —
  61 место/1000, школы — 113 мест/1000 и т. д.). Значения конфигурируемые,
  `approved_by_customer=false` до утверждения.
- `population` — из `municipalities.population` (демо-источник с указанием года).

**Классы нагрузки** (`config/thresholds`, палитра §8):

| Класс | Условие | Цвет | Паттерн/знак |
|---|---|---|---|
| Дефицит | index < 0,7 | `#D32F2F` | штриховка + `!` |
| Пограничное | 0,7 ≤ index < 1,0 | `#F9A825` | точки + `~` |
| Норма | 1,0 ≤ index < 1,5 | `#7CB342` | — |
| Повышенная обеспеченность | index ≥ 1,5 | `#2E7D32` | — |
| Нет данных | — | `#BDBDBD` | штриховка + `?` |

**Композитный индекс** — средневзвешенное по сферам (веса `SPHERE_WEIGHTS`, по умолчанию
равные) с поправкой на плотность населения:

```
pressure = (1 − provision_index) × normalized_density
```

чем плотнее население при том же дефиците, тем выше приоритет. Режимы отображения:
`обеспеченность`, `плотность населения`, `дефицит с учётом плотности`.

**Дисклеймер:** данные по плотности населения могут происходить из разных источников
(Росстат / операторы связи); методика и пороги — оценочные.

## 2. Индекс удовлетворённости граждан (Ф7)

Реализован в одном месте — `@oks/shared/utils/satisfaction`
(`computeSatisfactionIndex`), покрыт unit-тестами. Параметры — `SATISFACTION_WEIGHTS`.

```
satisfaction_index (0–100) =
    100 × [ w_resolved × resolvedShare
          + w_speed   × speedScore
          − w_overdue × overdueShare
          − w_repeat  × repeatShare ]
```

где `speedScore` — линейная шкала медианного времени ответа: `targetResponseDays`
(10 дн.) → 1, `maxAcceptableResponseDays` (30 дн.) → 0, вне диапазона — обрезается;
при отсутствии данных о времени — нейтраль 0,5. Веса по умолчанию:
`w_resolved=0.4`, `w_speed=0.25`, `w_overdue=0.2`, `w_repeat=0.15`.

При числе обращений < `MIN_APPEALS_FOR_INDEX` (=5) индекс **не рассчитывается**
(«нет данных») — защита от нерепрезентативных малых выборок.

**Визуализация:** (а) хороплет по МО (градация зелёный→красный), (б) тепловая карта по
точкам обращений (плотность) — hexbin-агрегация на бэкенде + полигональный слой
(воспроизводимо; см. `DECISIONS` D10). Фильтры: отрасль, период (месяц/квартал/год),
тип обращения, статус решения.

## 3. Зоны пешей доступности и отчёт доступности (Ф4) — реализовано

### 3.1 Построение зоны

| Шаг | Что делается | Где |
|---|---|---|
| 1 | Запрос `POST /isochrone/2.0.0` (Isochrone API 2ГИС): `start={lat,lon}`, `durations=[600,900]` (настраиваемо 5/10/15/20 мин, ≤ 5 значений, каждое ≤ 3600 с), `reverse`, `transport="walking"`, `detailing`, `detailed_response=true` | `integrations/2gis/isochrone.provider.ts` |
| 2 | Ответ `format:"wkt"` → `MULTIPOLYGON` разбирается собственным парсером в GeoJSON (POLYGON нормализуется в MultiPolygon — тип колонки в БД) | `integrations/2gis/wkt.ts` |
| 3 | Геометрия пишется в `isochrone_cache` вместе с `start_point`, `area_m2` (`ST_Area(geom::geography)`), `provider`, `is_mock`, `expires_at = now() + 30 суток` | `modules/isochrone/isochrone.service.ts` |
| 4 | При попадании в кэш повторный запрос к API **не выполняется**; параллельные одинаковые запросы склеиваются (single-flight) | там же |

**Направление (§7 Ф4):** `reverse=false` — «от объекта» (куда можно дойти),
`reverse=true` — «к объекту» (откуда жители дойдут); для садов/школ/поликлиник основной
сценарий — «к объекту».

**Объекты без точной геометрии** в расчёт не включаются (§6.3 п.7). Исключение — явное
согласие пользователя (`allowApproximate=true`): расчёт от центроида МО, результат помечается
`locationApproximate=true` в API и в UI.

**Демо-режим.** Без `ROUTING_API_KEY` геометрию пешеходной сети получить неоткуда.
При `ISOCHRONE_MOCK_GEOMETRY=true` зона строится **явной геометрической моделью**:
`радиус(азимут) = duration × WALKING_SPEED_MPS × (1 − a/2 + a·noise(азимут))`,
`a = MOCK_ZONE_ANISOTROPY`, шум — детерминированный `mulberry32(seed = id объекта + длительность)`.
Такая зона помечена `isMock=true`, `source="model"`, отдельным дисклеймером и бейджем
«ДЕМО-ДАННЫЕ» во всех поверхностях; в кэше хранится с `is_mock=true` и **никогда** не
выдаётся при `ISOCHRONE_PROVIDER=live`. При `ISOCHRONE_MOCK_GEOMETRY=false` адаптер
возвращает `provider_disabled`, а UI — «Нет данных» (см. `DECISIONS` D18).

### 3.2 POI внутри зоны (§4.4)

Геометрия зоны передаётся в Search API **тем же WKT** параметром `polygon` (§4.6 —
конвертация не требуется) плюс `region_id=36`, `page_size=50`, `fields=items.point,
items.rubrics,items.address,items.full_address_name`. Рубрики — из конфига
`config/poi_rubrics.ts` (по сферам: детсады/школы, поликлиники/амбулатории/стационары,
спортсооружения и площадки, ДК/библиотеки/музеи, энергообъекты; отдельно — жилые дома).
Сопоставление элемента выдачи со сферой — по `items.rubrics[].alias` и `items.purpose_name`,
**не по тексту названия**.

**Ограничение Search API и обходной путь.** Документация задаёт допустимую площадь
`polygon` ~6 км². Зона 20 минут пешком (~5 км²) находится на границе, поэтому при площади
больше `SEARCH_POLYGON_MAX_KM2` запрос выполняется документированным способом
`point` + `radius` (≤ 50 000 м при наличии `q`/`rubric_id`) с **постфильтрацией** результатов
попаданием точки в полигон (`pointInMultiPolygon`). Способ запроса возвращается в поле
`method` и показывается в отчёте.

**Защита квоты (§4.5):** не более `POI_MAX_PAGES` страниц на запрос рубрики, кэш снимка
в `isochrone_cache.poi_snapshot` (TTL `CACHE_TTL_POI_DAYS`), счётчики вызовов в
`GET /api/v1/isochrone/status`.

**Демо-режим:** без `CATALOG_API_KEY` POI не запрашиваются и **не выдумываются** —
в отчёте `count=null`, `gapReason="provider_mock"`, в UI «Нет данных».

### 3.3 Население и жильё в зоне

```
жители_в_зоне = density_per_km2(МО) × площадь_зоны_км²
```

- `density_per_km2` — из `municipalities` (население / площадь); источник и год указываются
  рядом со значением. На MVP население — `data/mock/population.csv` (`isMock=true`,
  бейдж «демо-население»); боевой источник — Росстат/операторы связи (этап 2).
- Оценка предполагает равномерное распределение населения внутри зоны — это указано в
  `method` показателя и в тултипе.
- Число жилых домов — только из POI 2ГИС (рубрика «жилой дом»); в демо-режиме «Нет данных».

### 3.4 Объекты той же сферы и вердикт

Соседние объекты берутся из **реестра ОКС** (реальные данные, `ST_DWithin` вокруг зоны,
радиус `ISOCHRONE_PEERS_RADIUS_M`): расстояние — гаверсинус **по прямой**, время —
оценка `distance / WALKING_SPEED_MPS`. Маршрут «от двери до двери» не рассчитывается:
Routing API 2ГИС на текущей подписке недоступен (§4.6, HTTP 418) — это ограничение
зафиксировано в UI и в `DECISIONS` D20.

Правила вердикта (`config/isochrone.ts → ACCESSIBILITY_THRESHOLDS`, значения требуют
утверждения заказчиком):

| Вердикт | Условие |
|---|---|
| `duplicates` — «возможное дублирование» | объект той же сферы **внутри зоны** на расстоянии ≤ `peerDuplicateM` (500 м) |
| `closes_deficit` — «закрывает дефицит в МО X» | жителей в зоне ≥ `minPopulationInZone` (300) **и** ближайший объект сферы ≥ `peerFarM` (1500 м) либо отсутствует |
| `improves` — «улучшает доступность» | зона построена, признаков дублирования и выраженного дефицита нет |
| `insufficient_data` — «нет данных» | зона не построена |

Достоверность (`confidence`): `high` — боевые изохроны + боевые POI + боевое население;
`medium` — частично демо-данные; `low` — зона построена демо-моделью.

**Ограничение методики (обязательно показывается в UI):** реестр ОКС описывает объекты
капитального строительства, а **не** полную сеть социальной инфраструктуры, поэтому
вердикт предварительный и уточняется (а) POI 2ГИС в боевом режиме и (б) индексом
обеспеченности МО `provision_index` (раздел 1, Ф5 — итерация 5).

### 3.5 Пакетный режим: покрытие и «белые пятна»

Расчёт — в PostGIS, без передачи тяжёлой геометрии в браузер для вычислений:

```sql
sel  = изохроны из кэша (транспорт, длительность, направление, режим провайдера,
       срок действия) ⋈ объекты под фильтром (сфера/отрасль/МО/статус)
uni  = ST_Union(sel.geom)
покрыто_МО   = ST_Area(ST_Intersection(m.geom, uni)::geography) / 1e6
белые_пятна  = ST_Difference(m.geom, uni)          -- упрощение 0.0008° для отрисовки
доля_покрытия = покрыто_МО / area_km2(МО)
жители_в_покрытии = density_per_km2(МО) × покрыто_МО
```

Если под фильтром в кэше нет ни одной зоны, покрытие и «белые пятна» возвращаются как
`null` с `hasData=false` и пояснением — **территория не объявляется непокрытой** без
реально рассчитанных зон (§15.1). Объекты без точной геометрии считаются отдельно
(`objectsWithoutGeometry`) и в покрытие не попадают.

**Дисклеймер (§7 Ф4, обязателен в UI):** «расчёт по пешеходной сети 2ГИС, является оценкой».

## 4. Производные показатели закупок (Ф6, итерация 6)

«Стоимость за м² / за место» = цена контракта / площадь (или мощность). Индикатор риска:
срок исполнения истёк при готовности < 100 %; неоднократные переносы сроков. На MVP —
мок-цены (детерминированные, `isMock`), см. `INTEGRATION_EIS.md`.

## 5. Объекты риска (Ф9)

Реализовано (`GET /api/v1/analytics/risks`): срок контракта истёк при готовности < 100 %.
Дополнительно (следующие итерации): готовность не растёт между снимками реестра;
отсутствие фотофиксации > N месяцев.
